## 用語

- 定義していない用語や勝手な造語を導入しない。
  その分野で確立した術語を使い、新語が必要なら初出で定義する。
- 固有名詞の読みや永続的な命名を推測で決めない。

## 検証

- 確認できていないことを断定しない。
  事実と推定を分ける。
- ファイル、設定、数値、過去の判断を引用するときは原典を確認する。
- 1回の観測を一般化せず、結論に必要な範囲を検証する。
  実装方針を左右する主張は、反証できる最小の確認を行う。
- 調査で実装の前提が変わった場合は、着手前に報告して方針を確認する。
- バグ修正の回帰テストは、修正前に失敗し、修正後に成功することを確認する。
  バグが変える観測可能な値を直接 assert する。

## Markdown read

- Markdown の長さが不明、または必要な節だけ読めばよい場合は、全文読みせず `markdown-context` skill を使う。

## Markdown edit

- Git 管理対象かどうかにかかわらず、リポジトリを保存先とする Markdown 文書は、一文ごとに改行し、段落の区切りを空行で示す。
  チャット、issue と PR の本文・コメントには適用しない。
