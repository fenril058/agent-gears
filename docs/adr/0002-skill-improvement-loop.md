# 実利用で観測された失敗から skill を更新する loop を持つ

agent-gears は、skill へのフィードバックを捕捉し、それを skill の編集提案へ変える loop を持つ。
構成は 2 skill とする。

- `skill-feedback`: 観測を `skill-feedback` ラベル付き GitHub issue として1件記録する。
- `skill-improver`: 未解決の issue を読み、出典で検証し、1つの skill への最小の編集を PR として提案する。

記録先は GitHub issue、起動は人間による手動とする。
定期実行はしない。

## なぜ

skill へのフィードバックはセッションが終わると消える。
このリポジトリは skill をファイルとして持ち、変更が PR review を通る構造を既に備えており、`ctx` が 568 セッションを索引している。
欠けていたのは、失敗に印を付ける経路と、それを編集提案に変える観測者の2つだけである。

着想は Warp の self-improving agents の報告(2026, Claude blog)による。
skill を取り込んだわけではないので `PROVENANCE.json` の対象ではない。
そこで有効とされた点のうち、このリポジトリで採用したのは次である。

- フィードバックは、その場で低摩擦に捕捉しなければ流れが続かない。
- 詳しい理由を伴う少数のフィードバックは、理由の無い多数に勝る。
- 規則の列挙ではなく理由を書くほうが、次の場面へ一般化する。
- 更新は skill ファイルの PR として流れ、人間の merge が loop を閉じる。

## ADR 0001 との関係

抵触しない。
ADR 0001 は health check を「静的監査と first-party tooling による非因果的な点検」と定義し、その対象に「実利用で観測された失敗」を明示的に含めている。
この loop はそこに収まる。

したがって `skill-improver` が主張してよいのは、ある文言があれば引用された特定の結果が変わったはずである、という点だけである。
skill が良くなった、挙動が測定可能に改善した、比較を実施した、のいずれも主張しない。
測定された効果を主張するなら ADR 0001 の隔離条件が必要であり、この loop はそれを満たさない。

## 想定される失敗

このリポジトリ固有のリスクは、信号が弱いまま observer を動かすと、実行を正当化するために編集を捏造することである。
PR #60 で削除した 185 行は、まさに根拠の無い一般論の policy だった。
制約の無い improver は、それを再生産する機械になる。

構造で対処する。

- 既定の出力は「変更なし」とし、それを完全な結果として扱う。
- issue 本文は証拠ではなく参照として扱い、出典を読むまで事実と見なさない。
  検証できない発生は落とす。
- 各 hunk は発生を引用する。引用できない編集は提案しない。
- 削除を一級の結果として明示する。実績はそちら側にある。
- 1回の実行で 1 skill、1 PR に制限する。

## Considered options

記録先:

- **GitHub issue にラベルで貯める。**
  採用。任意のマシンから `gh` で引け、リポジトリに走り書きが増えず、durable に残る。
- tracked ファイルに追記する。
  会話から離れずに書けるが、走り書きが tracked ファイルに溜まる。
- 新しい記録先を作らず `ctx` だけから拾う。
  摩擦は無いが、何が失敗かの判定を observer 自身が行うことになり、捏造リスクが最も高い。

起動条件:

- **溜まったら人間が手動で起動する。**
  採用。空振りの実行が発生しない。
- 定期実行(cron / GitHub Actions)。
  Warp と同じ形だが、あちらは週 400k セッション規模である。
  記録が空の週にも起動し、「何か出さねば」という圧力が残る。
- 記録が N 件溜まったら自動起動。
  空振りしないが、閾値を決める根拠が現時点で無い。

## Consequences

`skill-feedback` ラベルを GitHub 側に用意する必要がある。

improver の出力は PR であり、merge は人間が行う。
issue は merge 時に人間が閉じる。improver は閉じない。

この loop が空振りを続ける、あるいは捏造を止められないと判明した場合は、2 skill を削除して supersede する ADR を書く。
その判断材料は improver の実行結果そのもの(提案した PR と、その採否)であり、別途の測定基盤は導入しない。
