# sanity review プロトコル

feature/bugfix/refactoring の変更をレビューし、レビュー報告書を作成する。
報告書はレビュー完了を示し、修正点がある場合はそれを説明するために次工程へ渡すものである。
PR があればそこに貼り、無ければその実行環境の共有手段で渡す。

**この skill を起動することと、full review を行うことは同義ではない。**
full review は workflow である。
implementation session が変更を宣言し context を handoff し、**別の** review session がこのプロトコルを実行し、その報告書が修正を行う側へ戻る。
この skill はその workflow のうち reviewer の工程だけを担う。
前後の工程が欠けていてもレビュー自体は走るが、それは degraded な実行であり、報告書にその旨を書かなければならない。

## この skill の位置

```text
Implementation session
  |   change declaration + context handoff + code revision
  v
Review session  (この skill)   <-->   independent consultant
  |   レビュー対象 revision に bind されたレビュー報告書
  v
Fix session / human
```

## レビューの mode

他の何よりも先に mode を確定する。
報告書全体はこの mode を前提に読まれる。

### full independent review(推奨)

この session は当該変更を実装しておらず、実装時の対話も持っていない。
変更について知っていることはすべて明示的な入力として届く(「レビューの入力」を参照)。

session を分ける目的は、新しい session を開くという儀式ではない。
implementation の対話には暗黙の前提・自己正当化・既存仮説が乗っており、それを継承した reviewer には、その前提が隠している誤りが見えないからである。
fresh session は、change declaration・context・コードを「思い出した結論」ではなく「読み直す証拠」として扱わせる。

### self-review(degraded)

この session が当該変更を実装した、または実装時の対話を保持している。

self-review は禁止しない。
安価で即座に行え、実際に欠陥も見つかる。
ただし full independent review と同等ではなく、報告書をそう読めるように書いてはならない。
レビューの mode として記録し、自分自身の以前の推論こそ最も疑いにくいことを前提に作業する。

どの session で動いているかを skill 側から検出する手段は無いため、この申告は実行するAgent自身が行う。
レビュー対象の変更を自分が作ったのなら、報告書にそう書く。

## レビューの入力

review request は、何がそれを運ぶかによらず、次の3種類の証拠である。
レビューを始める前に3つとも特定し、実際に得られたものを記録する。

### 1. change declaration

実装者がこの変更について主張している内容。
なぜ変更したのか、何を変更したのか、何を変更していないと主張するのか、成立していると主張する invariant、意図的な non-goal / scope boundary。

GitHub adapter ではこれは PR 概要欄であり、加えて実装者自身の PR コメントとレビュー本文である。
それ以外の環境では、呼び出し側が渡す変更の説明がこれにあたる。
存在しない場合、手順2は評価対象を持たない。
diff から再構成して埋めるのではなく、不在として記録する。
自分で書いた宣言はコードと矛盾しえない。

### 2. context handoff

コードからは読めないもの。
設計意図とその根拠、却下した代替案とその理由、発見された制約、検証済みの事実、注意が必要な難所。

通常の producer は `conversation-context-export` である。
GitHub adapter ではその出力が PR コメント、`.dev/contexts/` 配下のファイル、またはその両方として届く。

**handoff された context は authority ではなく evidence である。**
そこに記録された設計判断・制約・却下理由・意図的な non-goal は実装者の主張であり、レビューの対象そのものである。
書かれているという理由だけで前提として採用しない。
可能な限り repository・コード・外部の証拠と突き合わせて検証する。
手順6がそれを明示的に行う工程である。
これは change declaration についても同じである。

### 3. code revision / diff reference

実際に何をレビューしたのかを、後から特定できる形で示すもの。
repository または worktree、レビュー対象の head revision、比較基準(base revision または diff range)。

これが報告書をコードの状態に bind する。
これが無ければ報告書は名前のない何かについての意見であり、後からまだ有効かどうかを誰も判定できない。

### transport はこの contract に含まれない

この skill は、呼び出しが利用可能にしたものを消費するだけである。
これらの artifact をどこに保存し、session 間をどう運ぶかは定義しない。
GitHub では PR がたまたま3つとも同時に運んでいる。
それ以外では、declaration と handoff は呼び出し側が渡し、revision は git が与える。
入力が得られない場合、それは記録すべき degradation であって、transport を発明する理由ではない。

## 対象外

- ライブラリ更新PR(dependabot/renovatebot等)は `library-update-review` skillの対象であり、このスキルの対象外

## 手順

### 手順0: レビューの枠組みを確定する

#### 0-1. レビューの mode を判定する

full independent review か self-review か(「レビューの mode」を参照)。
ここで確定して記録する。
報告書のヘッダーに入り、かつ「自分が実装者の主張に同意した」ことの重みを左右する。

#### 0-2. レビューの入力を集める

**GitHub adapter.** 引数でPR番号またはURLが指定されている場合はそのPRを対象とする。
指定がない場合は、現在のブランチに紐づくPRを自動検出する。

```
gh pr view {PR番号またはURL} --json number,title,body,url,author,comments,headRefName,headRefOid,baseRefName,baseRefOid
```

自動検出の場合は `{PR番号またはURL}` を省略する。

以下の情報を取得する:

1. PR本文(概要欄) = change declaration の中心。実装者本人のコメントとレビュー本文(2〜4)がこれを補う
2. PRコメント: `gh pr view` の comments
3. インラインレビューコメント: `gh api repos/{owner}/{repo}/pulls/{number}/comments --paginate`
4. PRレビュー: `gh api repos/{owner}/{repo}/pulls/{number}/reviews --paginate`
5. 差分: `gh pr diff {number}`

**PR が無い場合.** PR が無いという理由だけで終了しない。
PR は adapter のひとつであって、レビューの入力そのものではない。
change declaration とレビュー対象を呼び出しから取る。
引数の revision range、ユーザーからの変更の説明、あるいはその両方である。
引数にも対話にも対象が示されていない場合は、AskUserQuestionツールで、どの revision range をレビューするのか、change declaration はどこにあるのかを確認する。
ユーザーが渡せる change declaration を持っていない場合でも diff のレビューは行ってよい。
その場合、change declaration の不在を degradation として記録し、手順2のチェックリストは評価不能として扱う。

#### 0-3. レビューを revision に bind する

レビュー対象を保持している worktree で、何をレビューしているのかを記録する:

```
git -C {worktree} rev-parse HEAD &&
git -C {worktree} status --porcelain &&
git -C {worktree} log --oneline {比較基準}..HEAD
```

- **レビュー対象 revision**: レビュー対象の head commit。GitHub adapter では `headRefOid`、それ以外では `HEAD`。
- **比較基準**: 変更を読む際の起点となる commit または range。`gh pr diff` は merge base からの差分を出すので、GitHub adapter では `git merge-base {baseRefOid} {headRefOid}` を記録する。`baseRefOid` 単体は base ブランチの現在の先端であり、そのブランチが進むと動く。それ以外では、明示された range か、統合先ブランチとの merge base。
- **未コミットの変更**: `git status --porcelain` が空でなく、その変更がレビュー対象に含まれる場合はその旨を明記する。報告書は revision だけからは復元できない状態に bind されることになり、それ自体が報告に値する。

両端は、信用する前に確認する。
各 revision が local に存在することを `git -C {worktree} rev-parse --verify {SHA}^{commit}` で確認する。
fresh checkout には base ブランチの object が無いことが多く、その場合 `git merge-base` は使える基準を返すのではなく失敗する。先にその ref を fetch する。
worktree の `HEAD` が、報告しようとしている revision であることも確認する。
PR の head がここに checkout されていない場合は、依頼された revision ではなく、実際に読んだ revision を報告する。

変更のタイトル、PR があればその番号、ブランチ名は報告書のヘッダーに使用する。
Reviewed atには現在の日時(YYYY-MM-DD HH:mm:ss)を、Reviewerには自分のAgent名を記入する。

### 手順1: context handoff の読み込み

以下の順序で context handoff を探す。
呼び出しですでに渡されている場合(依頼に貼られている、path で示されている)は、それを使い探索は行わない。

#### 1-1. PRコメント欄を確認

PRコメントの中に「対話コンテキスト」というタイトルを含むコメントがないか確認する。
見つかった場合はその内容を対話コンテキストとして使用する。

#### 1-2. .dev/contexts/ を確認

ブランチ名をサニタイズ(`/ \ : * ? " < > |` を `-` に置換)し、`.dev/contexts/{サニタイズ済みブランチ名}.md` を探す。
見つかった場合はReadツールで読み込む。

1-1 と 1-2 はいずれも `conversation-context-export` が現在の出力先としている場所である。
これらは adapter であって定義ではない。別の手段で届いた handoff も同じ証拠であり、同じように扱う。

#### 1-3. 見つからない場合

AskUserQuestionツールで以下を確認する:

- **context handoff なしで続行**: 手順6(考慮漏れの確認)はスキップし、degradation として記録する
- **中断**: ユーザーに context handoff の準備を依頼する

#### 1-4. 対話コンテキストがリンクする ADR を辿る

ADR に記録された決定について、対話コンテキストは要約しか持たない。根拠は ADR 側にある(`conversation-context-export` 参照)。
コンテキストがリンクする ADR はすべて読む。
読まなければ要約を相手にレビューすることになり、意図して記録された決定を、説明のない場当たりな選択として読んでしまう。

diff が ADR ディレクトリまたは `CONTEXT.md` に触れている場合は、その変更もここで読む。
決定や定義を変える変更は、自分の diff についてではなくコードベース全体について主張しているからである。

ADR を読むことは ADR に従うことではない。
何がなぜ決まったかを知るためであり、それを再評価するのが手順6である。

### 手順2: change declaration の品質評価

**この手順はコードを読む前に行う。** コードの整合性確認に引っ張られて宣言の構造的問題を見落とすことを防ぐため。

実装者は正気ではないかもしれない。よくわからずに宣言を書いたり、AIに生成させてそのまま貼っているかもしれない。
この手順では宣言だけを読み、レビュアーがこれを読んで「変更の妥当性を判断できるか」を評価する。

#### change declaration チェックリスト

以下の4項目を **必ず全て** 評価し、結果をメモする。全項目を評価してから次の手順に進む:

1. **変更前の動作・問題が説明されているか**: レビュアーは変更の妥当性を判断するために、変更前の状態を知る必要がある。「何をやったか」だけでは「もしかしたら変更前の動作の方が正しかったのでは?」という疑問が残る
2. **「問題→解決」や「現状→修正」のペアで書かれているか**: 新機能の場合は目的・動機でも可。ただし「やったこと」だけの一方通行な説明は不十分
3. **変更の範囲が明確か**: 何を変えて、何を変えていないのか、どの non-goal を意図的に宣言しているのかがわかるか
4. **実装者自身の理解が見えるか**: AIが生成した文章をそのまま貼っただけでなく、実装者が何を考えてこの変更をしたのかが伝わるか

change declaration がまったく存在しない場合(手順0-2)は、4項目すべてを評価不能として記録し、結論でもその旨に触れる。
誰も説明していない変更であること自体が指摘事項である。

### 独立した相談の共通方針

手順3・手順4・手順5では independent consultant にセカンドオピニオンを求める(ただし手順4の「長期視点で命名・設計を考察する」サブセクションは対象外)。手順6では疑わしい点がある場合に限り相談する。以下のフォールバック順序に従い、**推測で判断せず実際に呼び出して試す**こと:

1. Skill toolで `subagent-consultation` を呼び出す。失敗した場合は2へ進む
2. main agentが単独で作業を実行する

`subagent-consultation` を呼び出す際は、**深さ**(「よく相談して」)と**具体的な質問**を同一ターンで伝えること。これが以下各手順の `Args:` の内容である。深さを先に伝えることで、consultation 側がユーザーに聞き返してレビューが中断するのを防ぐ。「失敗した場合」とは、skill が利用不可、または単発の呼び出しでエラーになった場合を指す。再試行はせず、2 へフォールバックする。

#### 相談先の独立性とは何か

独立性は「別モデルファミリであること」ではない。
それは独立性の1つの軸についての heuristic にすぎない。
ここで意味を持つ軸は次のとおり。

- **session / 対話コンテキストの独立**: 相談先が implementation の対話も、こちらの対話も継承していない。
- **model / prior の多様性**: 訓練が異なるため、盲点が異なる。
- **独自の調査**: 相談先が repository を自分で読み、主張を自分で検証する。こちらの要約を採点するのではない。
- **tool / 実行環境の差**: 違うチェックを走らせられる相談先は違う失敗をし、こちらの環境が隠しているものを見つける。
- **反論する役割の明示**: 相談先に、同意ではなく反論を求めている。

これらは独立した2つのレイヤーに乗っており、一方が他方を代替しない。

- **implementation → reviewer**: 手順0-1で記録した mode。別ファミリの相談先を使っても、self-review が independent review に変わることはない。
- **reviewer → consultant**: この節。fresh review session であっても、セカンドオピニオンが不要になることはない。

**どの相談先を使うか。** 相談先の選定は `subagent-consultation` 側が行うが、手順ごとに必要な種類が違うので、それを伝えること。
手順3・手順5・手順6は、コードと実装者の主張が**正しいか**を問う。よって priors が自分と独立した相談先、実務上は別モデルファミリ(Claude Code なら Codex)を、コスト増に見合うものとして優先する。
手順4は判断ではなく既存コードベースの読解なので、同ファミリのsubagentで足りる。
以下各手順の `Args:` にこの指定を含めてある。別ファミリの相談先が実行環境に無い場合は consultation skill 側でフォールバックされ、レビューは続行する。

優先順位

```text
別モデルファミリ > 同ファミリの fresh な相談先 > reviewer 単独
```

は prior の多様性についての heuristic であって、独立性の定義ではない。
実装者の結論を確定事実として書いた prompt を渡された別ファミリの相談先は、ほとんど独立していない。
逆に、同ファミリでも repository を白紙から読み、反対側の立場で論じるよう求められた相談先は、本物のセカンドオピニオンである。
prompt では結論ではなく、問いと証拠を渡すこと。

ここで起きうるフォールバックは2種類あり、記録の仕方が違う。
**tier fallback**(別ファミリを求めた手順に同ファミリの fresh な相談先が答えた場合)は、independent consultation が成立している。
ヘッダーにはどの tier が答えたかを記録し、フォールバックしたこと自体は「レビュー作業において発生した問題」セクションに書く。
ヘッダーに「independent consultation なし」と書くのは、**どの相談先も答えなかった場合**(上記の 2)だけである。

**2(main agent単独実行)にフォールバックした場合**は、このスキルのコアである批判的思考の連鎖(互いの主張を検討・反論しあい、正確性と網羅性を向上するプロトコル)が機能していないことを意味する。往復検証が欠落した状態でのレビューは本来の精度を持たないため、報告書の「レビュー作業において発生した問題」セクション冒頭に、以下の文言をそのままbold段落として記載すること:

**⚠ 警告: 批判的思考の連鎖が機能していません、実行環境が正気である事を疑ってください**

各手順では、相談先に渡すArgsの内容と、結果の扱い方を記載する。

### 手順3: 実装者の説明と実装の整合性確認

この手順の目的は、change declaration やコメントでの説明と実際のコードが一致しているかを確認する、**ドキュメントとコードの読み合わせ** である。

change declaration が存在しない場合(手順0-2)、以下の確認事項1と3は該当なしになる。
context handoff があれば確認事項4だけを行い、照合対象を作るために diff から declaration を再構成することはしない。

#### 重要: 実装者の発言のみを拾う

change declaration の author と、各コメントの author を照合し、**実装者本人の発言のみ**を実装の説明として扱う。
他の人が書いた応援コメント、機能に対する期待を込めたコメント、質問等は、実装の説明ではない。
これらを実装の説明と混同すると、整合性の判断を誤る。

#### 確認事項

1. change declaration の説明と、実際の差分が一致しているか
2. インラインレビューコメントでの実装者の説明と、実際のコードが一致しているか
3. PRレビューの本文(top-level review comment)での実装者の説明と、実装が一致しているか
4. context handoff の内容と、実装が一致しているか(handoff がある場合)

齟齬を発見した場合は具体的に記録する。

#### 相談先による整合性確認

Agent自身の確認に加えて、相談先にも差分と change declaration の整合性を確認させる。
別の視点でコードを読むため、Agentが見落とした齟齬を発見できる可能性がある。

「独立した相談の共通方針」に従い、以下のArgsで呼び出す:

```
Args: よく相談して。別モデルファミリの相談先を優先してほしい。{PR #番号 または revision range} について、実装者が主張している変更内容と実際の差分に齟齬がないか確認してほしい。{宣言の要約と確認ポイント}
```

相談先の指摘を受け取ったら、自分の確認結果と照合し、見落としがなかったか確認する。

### 手順4: 命名・設計パターンの一貫性

この手順の目的は、実装が既存のコードベースの慣習と一致しているかを確認する、**コードベースの読み解き** である。
バグ・脆弱性を調べる前にコードベースを理解することで、後続の調査の精度が上がる。

#### 確認事項

1. **命名規則の一致**
   - ファイル名・関数名・変数名・クラス名が、既存コードの命名パターンと揃っているか
   - 機能の正式名称を歯抜けに省略した名前が導入されていないか

2. **設計パターンの一致**
   - 構造・module分割・責務の切り方が、既存の類似機能と揃っているか
   - 既存の抽象化を活用しているか、重複した実装を作っていないか

齟齬を発見した場合は具体的に記録する。

#### 相談先による確認

Agent自身の確認に加えて、相談先にも命名・設計パターンの一貫性を確認させる。

「独立した相談の共通方針」に従い、以下のArgsで呼び出す:

```
Args: よく相談して。同ファミリのsubagentでよい。{PR #番号 または revision range} で追加・変更された命名と設計パターンが、既存のコードベースの慣習と一致しているか確認してほしい。{変更概要}
```

相談先の指摘を受け取ったら、自分の確認結果と照合し、見落としがなかったか確認する。

#### 長期視点で命名・設計を考察する

将来、コードベースが拡張されたときに、現在の命名・設計が禍根となりうるかを考察する。
既存コードとの一致(事実判定)とは異なり、これは議論のタネを提供して人間の想像力を掻き立てるための作業である。

気になった点があれば、「懸念・反証・結論または保留」を押さえた自問自答形式で書き出す。
これはAgent自身の見解なので、通常の段落として記載する。1論点につき2〜3段落程度でよい。
無理に結論を出さなくてよい。気になる点がなければ「特になし」と記載する。
この考察セクションは相談先には振らず、skill実行元のAgentが自分で考える。

出力例:

```markdown
「access-token」という名前は、現状はユーザーとサービス間のtokenしか指さないため問題はない。
ただ今後、外部サービスとの接続用のtokenが登場した場合は、概念衝突が起きる可能性がある。

そうなったら `user-access-token` のように主体を名前に含める必要が出るかもしれない。
もっとも、現時点で外部サービス連携を近い将来に追加する計画は見えていないため、今すぐ修正すべき問題ではないと判断する。
```

### 手順5: バグ・脆弱性の調査

「独立した相談の共通方針」に従い、相談先にコードレビューを依頼する。
引数には、変更概要、差分の要約、確認してほしいポイントを含める。

**深さの指定を引数に含める**こと。consultation系スキルは深さが未指定だとユーザーに聞き返すため、レビューの流れが中断される:

```
Args: よく相談して。別モデルファミリの相談先を優先してほしい。{PR #番号 または revision range} のコードレビューをお願いします。{変更概要と確認ポイント}
```

#### 結果の検証

相談先の指摘を鵜呑みにしない。以下を行う:

- 相談先が指摘したポイントを、自分でコードを読んで検証する
- 相談先が見落としている可能性がある領域を意識的に探す
- 相談先の指摘と自分の見解が食い違う場合は、両方の理由を記録する

### 手順6: context handoff の再読み・考慮漏れ確認

context handoff がない場合はこの手順をスキップする。

**コードレビューは作業結果のダブルチェックではない。結果ではなくプロセスをレビューする。**

やった事はコードを読めばわかる。検討した上でやらなかった事こそ、設計のレビューに必要な情報である。
context handoff に書かれた設計判断・却下理由・意図的な非対応の「プロセス」が正しいかを検証する。
この手順で handoff は、ブリーフィングであることをやめ、レビューの対象になる。

context handoff を改めて精読し、以下を検証する:

#### 6-1. 設計判断の根拠

context handoff に書かれた設計判断の理由が、コードの実態と一致しているか。

#### 6-2. 却下した代替案の再評価

context handoff の「却下した代替案」セクションから、各代替案を1つずつ抜き出して再評価する:

- 不採用の理由は妥当か。本当に公平に比較したか
- 見落とした利点や、過大評価したデメリットはないか
- 採用案と却下案の比較に使われた前提条件は正しいか

#### 6-3. 失敗した試行のプロセス検証

「試したがダメだった」と記載されているものについて、結果だけでなく**試し方自体**を疑う:

- 前提条件は正しかったか
- 実行手順に見落としはなかったか
- 判断基準(「ダメ」と判定した根拠)は妥当だったか
- 別の条件で試せば結果が変わる可能性はないか

#### 6-4. 意図的に対応しない事項の妥当性

「やらない」と決めたもの、および change declaration が主張する non-goal について:

- 「やらない」理由は、今の実装を踏まえても妥当か
- 実装の結果、前提が変わって「やるべき」に変わっていないか
- 実際のコードは、宣言された scope boundary の内側に収まっているか

#### 6-5. 記載されている事実の正確性

context handoff に書かれた「事実」が本当に正しいか、コードを読んで検証する。

疑わしい点がある場合は、「独立した相談の共通方針」に従い相談先にも相談する。Argsに「よく相談して」と、別モデルファミリの相談先を優先する旨を含めること。

### 手順7: レビュー報告書の作成

このSKILL.mdと同じディレクトリにある [TEMPLATE.md](TEMPLATE.md) を読み込み、その形式に従って報告書を作成する。

報告書は**会話に出力する**(ファイルに保存しない)。
次工程へ渡すのはレビュアー自身である(PRに貼る、あるいはその実行環境の共有手段で渡す)。

TEMPLATE の見出しは日本語だが、報告書は利用者の作業言語で書く。

#### 報告書の contract

書き方によらず、完成した報告書からは後の読み手が次を特定できなければならない。

- 何をレビューしたか。変更のタイトル、review target(PR 番号、または repository と範囲)、ブランチ
- レビュー対象 revision と比較基準。未コミットの作業ツリー変更が含まれていたかどうかも含む
- どの change declaration とどの context handoff を使ったか、およびその出所
- 指摘事項と、それぞれの扱い(要修正 / 修正が望ましい / 実装者への質問 / 現状で許容)
- レビューでは解決できなかった問い
- reviewer とレビュー日時
- independent consultation を実際に行ったか、行ったならどの種類の相談先か
- レビューの mode と、その他の degradation(宣言の不在、handoff の不在、相談先の不在、差分が大きく網羅できなかった等)

この一覧は報告書が備えるべき最小の意味である。TEMPLATE.md はその具体形のひとつで、上記の多くはヘッダーに落ちる。

#### 報告書作成のガイドライン

- **change declaration > サマリー**: 実装者の説明を引用・抜粋してbefore-afterで整理する。想像で補って勝手に書かない。実装者の説明が不十分な場合は素直にその旨を指摘する
- **change declaration > 品質評価**: 手順2のチェックリスト結果をOK/NG/該当なし/評価不能で記入する。NGの場合は具体的に何が不足しているかを記載する
- **指摘事項と扱いセクション**: 上記各セクションで挙げた指摘を1箇所に集約し、それぞれに扱いを付ける。扱いが暗黙のままの指摘は、修正する側にとって行動の起点にならない
- **未解決の問いセクション**: レビューで決着しなかった問いを書く。情報が足りない、検証手段が無い、実装者にしか答えられない、のいずれか
- **レビュー作業において発生した問題セクション**: レビュー手順をスキップした場合は、外的要因(ツールが利用できなかった等)かAgentの判断かを区別して記載する。問題がない場合は「特になし」と記載する
- **結論セクション**: 全体の総合判断と推奨アクションを記載する
- 全体を通じて、レビュアーが「この変更は妥当か」を判断するための材料を提供することを意識する

#### 報告書は1つの revision に bind される

報告書は手順0-3で記録した revision についてのものであり、それ以外については何も述べていない。
コードが動けば(commit の追加、rebase、force-push、指摘への修正)、報告書は古い revision についてのものになり、stale になりうる。

何に bind されているかを書いておくことで、次の読み手が「まだ有効か」を自分で判定できる。
コードが動いた後に再レビューを求められたら、revision の bind をやり直し、古い報告書の扱いをそのまま引き継がずに、新しい revision に対して指摘を再確認する。

## 関連スキル

- **subagent-consultation**: independent consultant に相談するスキル(Agentツール、または実行adapter経由の他ベンダーCLI)。手順3・手順4・手順5・手順6で使用する。Codex を含む相談先の選定もこのskillが行う

- **conversation-context-export**: 対話コンテキストを書き出すスキル。context handoff の通常の producer であり、その形式の背景知識
- **library-update-review**: ライブラリ更新PRのレビュースキル。このスキルの対象外である変更の種類
- **domain-modeling**: 記録層(`CONTEXT.md` と ADR)を担当するスキル。手順1-4 で辿る ADR の書式と supersede 規則の背景知識
