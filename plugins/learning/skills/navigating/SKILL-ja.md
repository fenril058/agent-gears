# Navigating 手順

ユーザーが対象の中を自力でたどれるようになるまで案内する。
対象が指定されていなければ、セッション内の直近の実装を使う。
読むのはユーザーであり、ユーザーがまだ読んでいないコードを先に説明しない。

最初に対象を調査する。
直近の差分や計画のような小さな対象は直接読む。
大規模または不慣れなコードベースを意味的に広く探索する場合は `fast-search` を使う。
大きな Markdown 文書には `markdown-context` を使う。
外部文書には適切なブラウジング手段を使う。

最初に経路を組み立て、旅程を示す。

- 各部分の関係を短く概説する。
- ファイルと行範囲、および目的を一行で添えた地点を順番に並べる。
- エントリーポイントと主要なデータ構造を、それを使う処理より前に置く。
- 主要な処理をエッジケースや詳細より前に置く。
- 安全なテスト、CLIコマンド、小さな確認実行を含む地点に印を付ける。

概説は地図にとどめ、案内そのものを先取りしない。
各地点では、行範囲と、振る舞い・状態・判断のいずれかに着目させる質問を1つ示す。
ユーザーが読んで自分の言葉で答えるまで待つ。

各回答を率直に評価する。

- 正しい点を確認する。
- 間違いを訂正する。
- 不足を補う。
- 密度の高い構造は、ユーザーが説明を試みた後でだけ分解する。

実行可能な地点では、先に結果を予測してもらう。
その後でユーザーに実行してもらい、結果と予測を突き合わせる。

回答が不確かなら先へ進まない。
範囲を狭め、焦点を絞った質問をし、もう一度読んでもらう。
再読しても詰まった場合にだけ説明する。
必要なら地点を分割し、旅程を更新する。

経路を完了し、ユーザーの回答が十分になったら終了する。
最後に、次を短い入れ子の箇条書きでまとめる。

- 地点ごとに1項目、詳細は1段まで。
- 類似コードにも応用できる読み方。
- ユーザーが苦戦した地点。
- その地点を対象にした、貼り付けて使える `quizzing` の呼び出し。
