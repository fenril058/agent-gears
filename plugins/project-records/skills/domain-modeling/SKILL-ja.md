# ドメインモデリング手順書

設計しながらプロジェクトのドメインモデルを能動的に構築・先鋭化し、結晶化したその瞬間に書き留める。

これは**能動的な**規律である。
`CONTEXT.md` を読んで語彙を借りるのは、どの skill でもできる一行の習慣にすぎない。
この skill が受け持つのはモデルを*変える*ときである——正典となる語を定める、いま言われたこととコードの矛盾を捕まえる、覆しにくい決定を記録する。

## どの層か

これは**記録層**である。記述対象のコードと一緒に commit され、一度書いたら不変の成果物を扱う。
対になる層が2つあり、区別は置き場所ではなく**更新モデル**である。

| 層 | sink | 更新モデル |
| --- | --- | --- |
| 揮発層(`conversation-context-export`) | `.dev/contexts/` + PR コメント | ブランチごとに再生成。commit しない |
| **記録層(この skill)** | `CONTEXT.md`、ADR ディレクトリ | **追記と supersede。書き換えない** |
| 永続層(`durable-knowledge-export`) | GitHub wiki または knowledge リポジトリ | living page。常に現在状態 |

ここにしか置けないもの: **このコードベースの語彙**と、**覆したことを記録として残したい決定**。
living page に置いた決定は「かつて別の決定だった」という事実を失う。この層が存在する理由はまさにその損失を防ぐことにある。

抱え込まず振り分けるもの:

- *この*変更の根拠、残作業、一度きりのデバッグ → 揮発層。
- 実測値、ツール評価、システム横断の落とし穴 → 永続層。

## セッション中に行うこと

### 用語集と突き合わせて指摘する

`CONTEXT.md` の既存の語法と衝突する語が出たら、その場で指摘する。
「用語集では『キャンセル』を X と定義していますが、いまの用法は Y に見えます。どちらですか」

### 曖昧な語を先鋭化する

語が曖昧または多義なら、精密な正典の語を提案する。
「『アカウント』とおっしゃいましたが、Customer ですか User ですか。これは別物です」

分野の術語と、プロジェクトの ubiquitous language を切り分ける。
**術語**には、その分野で確立した語を使い、自分で造語しない。
**ubiquitous language** は、1つのプロジェクトの中では1つの概念に1つの正典の語を選び、そこは断定的に決める。
分野の標準語がある場合はそれが勝ち、それが正典になる。断定的に選ぶのは、分野が等しく開いたままにしている語の間だけである。

### 具体的な場面で検証する

ドメインの関係を議論するときは、境界の際どい場面を具体的に立て、概念の境目について精密な言明を強いる。

### コードと突き合わせる

「こう動く」という言明が出たら、コードがそれに同意しているか確認する。
矛盾を見つけたら表に出す。「コードは Order 全体をキャンセルしていますが、いま部分キャンセルが可能だとおっしゃいました。どちらが正しいですか」

### その場で書く。最後にまとめない

語が確定したらその場で `CONTEXT.md` を更新する。
決定が下記の基準を満たしたらその場で ADR を書く。
セッションの最後にまとめようとすると記録は失われる——セッションが終わるか context が尽きて、固まったはずのものが蒸発する。

## 用語集

`CONTEXT.md` は用語集であり、それ以外の何物でもない。
実装の詳細、仕様、走り書きを入れない。
書式と単一/複数コンテキストのレイアウトは [CONTEXT-FORMAT.md](CONTEXT-FORMAT.md) を読む。

遅延生成する。最初の語が確定したときにファイルを作る。

## ADR

**3条件すべて**を満たすときだけ提案する。

1. **覆しにくい** — 後から考えを変える費用が無視できない。
2. **文脈なしでは意外** — 将来の読み手が「なぜこうしたのか」と思う。
3. **本物のトレードオフの結果** — 実在する代替案があり、特定の理由でこれを選んだ。

1つでも欠けたら書かない。
覆しやすいなら、覆せばよいだけである。意外でないなら誰も疑問に思わない。実在する代替案が無かったなら「当たり前のことをした」以上に記録すべきものが無い。

多くのセッションは、先鋭化した用語集と、ADR ゼロか少数を生む。
それが意図した姿である。

採番、supersede、テンプレートは [ADR-FORMAT.md](ADR-FORMAT.md) を読む。

### ADR ディレクトリを解決する

**`docs/adr/` を決め打ちしない。**
既存リポジトリには大抵すでに慣習があり、違う場所に書くと記録が二分される。
以下の順で解決する。

1. **既存の ADR ディレクトリ。** `docs/adr/`、`doc/adr/`、`docs/decisions/`、`docs/architecture/decisions/`、`adr/` を探す。ADR が入っているものがあればそれを使い、既存ファイルを何本か読んで採番・front matter・見出しの様式に合わせる。テンプレートを押し付けない。
2. **ツールの設定。** `.adr-dir`(adr-tools)がディレクトリパスを持つ。`.log4brains.yml`(Log4brains)はプロジェクト設定の中で指定する。
3. **どちらも無い** → `docs/adr/` を既定として作成し、そうしたこととその理由をユーザーに伝える。

最初の ADR を書く前に、解決したディレクトリを述べる。

## 関連スキル

- **grilling**: ここに記録されるものの大半を生むインタビュー。あちらがユーザーとの間で決定を固め、この skill が固まった端から書き留める。
- **conversation-context-export**: 揮発層。決定を ADR にしたとき、あちらは論拠を複製せず要約とリンクだけを残す。レビュアーはまずコンテキストを読み、リンクを辿る。
- **durable-knowledge-export**: リポジトリ外の永続層。システムについての横断的な知識はそちらであって ADR ではない。
