# エージェント向け指示ファイルを改善する

コードの仕組みの説明より、プロジェクトでの判断を変える指示を優先する。
利用者が意図する振る舞いと規約を保ち、短縮はその次に置く。

## 何を残すか判断する

対象ファイルと、編集案に関係する import、ローカル規約、決定を読む。
残す・削る・書き直す判断を左右する箇所で原典を確認する。
文書整理のために、リポジトリ全体の網羅的な監査を行う必要はない。

認証の設定要件は保つが、指示ファイルに秘密値そのものを新たに書き込んだり残したりしない。
見つけた場合は値を削除し、値を引用せずに存在していたことを知らせる。

- プロジェクト固有の制約、ツールの既定からの逸脱、責任範囲、作業の進め方を左右する前提条件を残す。
  見落としやすい追従編集や互換性の条件は、コードから再構成できても残す。
  導出できるという理由だけで、有用な注意を削除しない。
- 判断の指針を加えない一般的な助言、重複した説明、コードの構成一覧を削る。
  詳細は維持されている文書へリンクし、規則と正しく適用するために必要な理由は残す。
- 古いと思われる規則は、削除前に原典と照合する。
  現在のコードとの不一致は実装の欠陥や意図的な制約の可能性もあり、それだけで規則が失効したとは判断しない。
  焦点を絞って確認しても保護の目的が不明なら、残して不確実な点を示す。
  未解決の選択が意図する振る舞いを実質的に変え、依頼や利用可能な根拠から決められない場合だけ質問する。

残す規則は、条件と適用範囲を伴う具体的な行動へ書き直す。
たとえば「X を変更したら Y も更新する」とする。
圧縮の際に、局所的な規則を一般化したり例外を落としたりしない。
文書の規約に従い、関連する規則をまとめる。
各行の分類は必須にしない。

## 編集の範囲を保つ

失敗をきっかけに見直す場合は、表現や長さを原因とする前に、読込の有無、適用対象、陳腐化、競合を必要な範囲で確認する。
同じ間違いや回答済みの質問の繰り返しは、調査のきっかけであり診断結果ではない。

文書整理だけを理由に、新しい skill、hook、設定を作らない。
そうした変更は、依頼と既存の許可に含まれる場合に限る。
指示の置き場所や検査の実行方法を変える場合は、条件付き読込や強制実行を仮定せず、対象 host の読込・実行方式を確認する。
Claude Code でこれらの仕組みが関係する場合は、公式の [memory](https://code.claude.com/docs/en/memory) と [hooks](https://code.claude.com/docs/en/hooks) の資料を参照する。

## 確認と報告

差分を見て、制約の欠落、適用範囲の変化、規則の競合、参照切れを確認する。
変更ファイルに関係する既存の検査を実行する。
重要な編集とその理由、未解決の選択を要約する。
削除した各行の報告や、行数・トークン数の計測を定例にしない。
短縮や静的検査の成功だけでは、エージェントの振る舞いの改善は示せない。
改訂した指示に従うエージェントの行動を実際に確認したか明記する。

`empirical-prompt-tuning` は、実測評価または description と本文の整合確認を明示的に依頼された場合だけ使う。
通常の指示ファイル編集を理由に起動したり、新しい評価 runner を要求したりしない。
