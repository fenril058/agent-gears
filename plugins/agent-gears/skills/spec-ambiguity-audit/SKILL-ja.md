# 仕様の曖昧さの監査

与えられた文書から、推測なしでは実装者が決められない事項を探す。
プロジェクトの背景情報を持たない読解と原文による再確認を分け、慣れによる補完と誤読による指摘を抑える。

## 範囲と読解

依頼で許可された監査範囲に従い、同じ許可を聞き直さない。
監査だけの依頼では、仕様の書換や実装まで許可されたとは扱わない。
文書の範囲内で実装や観測可能な振る舞いを変える曖昧さ、矛盾、未定義の用語、欠落を対象とする。
対象外の機能や、実装者が自由に選べる事項の詳細まで要求しない。

短い文書の監査では、利用者が独立した読解を求めていなければ、文書を直接読む。
独立した読解を別のエージェントに依頼するのは、利用者が求めた場合か、大きな文書で主担当が無意識に補う前提を見つけるのに役立つ場合とする。
[references/prompt-template.md](references/prompt-template.md) を使い、文書と関連する参照先を渡す。
主担当の会話、プロジェクト概要、疑っている箇所、想定解は渡さない。
読み手の調査対象を渡した資料に限る。
無関係なコード、履歴、プロジェクトの記憶を使うと、監査の性質が変わる。

実行手段を選ぶ前に、現在のセッションで使えるツールと指示を確認する。
親の会話を引き継がずに起動できるサブエージェント（対応していれば `fork_turns: "none"` など）か、読み込む文脈を確認できる既存 CLI の新規実行を優先する。
どの指示や記憶が読み込まれるかも確認する。
別スレッドというだけでは背景情報なしの読解を満たさない。
十分な能力があり利用可能なら安価なモデルを選んでよいが、モデル選択と会話の継承は別の機能である。
適切なツールがあるのに手動のセッション切替を必須にしたり、監査のために host 設定を変更したりしない。

独立して実行する手段がなければ、その制限を明示し、現在のセッションで可能な原文確認を行う。
利用者が独立した読解を明示的に求めている場合は、その部分を未実施として報告する。
同じ会話での読み直しを、その代わりとして扱わない。

## 指摘候補の確認

独立した読み手のリストも含め、すべての指摘を確認するまでは候補として扱う。
主担当が原文と照合し、候補を挙げた読み手にリストの承認を求めるだけで済ませない。
引用箇所とその前後を読み、関連する定義、別の節、参照文書を確認してから、未解決の指摘として残す。
局所の抜粋に答えがないことを、文書に答えがない根拠としない。
必要な参照先を読めなければ、仕様が未記述と断定せず、確認の限界として示す。

複数の解釈や欠けた判断が実装に実質的な影響を与え、渡された資料でも決まらない場合だけ指摘を残す。
回答済みの疑問、誤読、重複、文書の範囲を超える要求は除外する。
却下した項目を残すために、疑問を狭めたり新しく作ったりしない。
答えを得るのに明記されていない推論が必要なら、明文の規則と区別し、実装の選択が未解決のままかを判断する。

長い文書で引用が疎らな場合は、[scripts/extract_context.py](scripts/extract_context.py) を任意で使い、重複した読み取りを減らせる。
スクリプトが行うのは本文の抽出であり、指摘の判断は主担当が行う。
余白を広げた範囲の重複や隣接をまとめられるよう、同じファイルの範囲は一度に渡す。

```bash
python3 <skill-dir>/scripts/extract_context.py <file> --margin 10 \
  --range 62 --range 316-318 --range 300-301
```

余白は該当箇所に合わせて選ぶ。
抽出しても、別節や参照先の確認は必要である。
短い文書や、抽出範囲が大半を占める場合は、原文を一度読む。

## 報告

未解決の指摘だけを、原文の位置、文書から決められない事項、実装への影響とともに報告する。
行番号を使えるなら使い、使えなければ節や引用で位置を示す。
要件の欠落は、それを必要とする節に結び付け、行番号を捏造したり、引用できないという理由だけで黙って除外したりしない。
報告の長さは指摘に合わせる。
指摘がゼロでもよく、固定の件数や表は求めない。
確認した資料、独立した読解の実施有無、結論に影響する制限を示す。
採用件数と総数の比は、文書の成熟度と候補リストの両方に左右されるため、監査の精度とは扱わない。
