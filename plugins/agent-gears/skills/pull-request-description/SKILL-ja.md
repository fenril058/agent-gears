# PR 本文

PR 本文は差分と一緒に読まれるものであって、差分の代わりではない。
冒頭に、レビュアーが方向づけできるだけの、変更が何をするかの 1〜2 文を置く。
残りは差分が答えられないことに使う。レビュアーが既に見ている内容を書き写しても、注意を余計に使わせるだけで、次の push で陳腐化する。

## 書く(優先順)

1. この変更が解決する問題と、いま解く価値がある理由。
2. 採った方針と、実際に代替案を比較した場合は、他を退けた理由。
3. 書かなければ差分から逆算するほかない設計判断。
4. 受入条件。正しいと言えるために何が成り立つ必要があり、それをどう確認したか。
5. レビューに必要な文脈。スコープの境界、既知の制限、follow-up、risk と rollback、最初に見るべき箇所。

各項目は、この変更に当てはまるときだけ書く。
小さな保守的変更なら、最初の2項目より先は要らないこともある。
実際には無かった項目を作らない。比較していない代替案や後付けの理由は、レビューを誤らせる。

## 転記しない

- 差分が既に示す件数と一覧。commit 数、変更ファイル数、ファイル一覧、行数、テスト件数。
- 実装の言い換え。どのファイル・関数が何をするようになったかの逐一の説明。
- commit や CI ページが既に表示しているバージョン番号、テスト名、CI job の状態。

これらを書くのは、論拠を担うときだけにする。
before/after の比較、受入条件、意思決定の根拠のいずれかである場合を指す。
「1 リクエストあたり 3 クエリが 1 クエリになった」は測定結果だが、「12 ファイル変更」はそうではない。

## 投稿前の点検

各行について問う。**これは差分、commit、テストコード、CI 結果が既に示しているものの網羅的な一覧、件数、逐一の説明か。**
そうなら削る。ただし比較、受入条件、意思決定の根拠であるものは残す。
冒頭の要約は残し、その裏づけとなる一覧は載せない。
削った結果、差分が語らないことを何も言っていない本文になるなら、必要なのは長い本文ではなく、変更の理由を書くことである。
