# 対話コンテキストのexport

次のセッションやレビュアーへ渡す文脈を、選択したworktreeの `.dev/contexts/{サニタイズ済みブランチ名}.md` に保存する。
記録の構造には [TEMPLATE.md](TEMPLATE.md) を使う。

## 依頼の範囲

一般的な「対話コンテキストをexportして」「.devに保存して」は、ローカル保存を既定とする。
PRコメントでの共有を依頼された場合、または今回のexportでの共有が会話内ですでに許可されている場合は共有し、同じ許可を取り直さない。
ローカル保存だけという明示的な指示があれば、その範囲に従う。
PRの存在や作成だけでは、対話コンテキストを投稿する許可にはならない。
保存先や共有範囲の特定に必要な情報が欠けている場合だけ確認する。

`.dev/contexts/` は、ブランチ単位の文脈を置く、コミットしない作業ツリー上のスクラッチ領域である（揮発層）。
`.dev/` を `git add` しない。
無視したい場合は、この生成物のためにリポジトリの除外方針を変えず、ユーザーのグローバルgitignoreを使う。
共有が許可されている場合はPRコメントを共有先とし、ローカル保存だけの場合はそのworktreeで利用する。
ブランチを越えて残すべき発見は、下の「関連スキル」に従って振り分ける。

## worktreeとメタデータの選択

別worktreeを含め、ユーザーが保存先を明示した場合は、ホストのfilesystem権限の範囲でその指定に従う。
指定がなければ、シェルの偶然の現在ディレクトリではなく、ホストが示すセッションのworkspace rootを含むGit worktreeを使う。
選択したpathからGit rootを特定し、その `{worktree root}` をすべてのファイルpathとGit/gh操作の基準とする。

```bash
git -C "{選択したpath}" rev-parse --show-toplevel
git -C "{worktree root}" branch --show-current
git -C "{worktree root}" rev-parse HEAD
```

保存ファイルを明示された場合は、実在する親ディレクトリから、そのファイルを含むworktreeを特定する。
保存先を合わせるために、兄弟worktreeを黙って選んだり、ブランチを切り替えたり、Gitの状態を変更したりしない。
保存先がGit worktree内になかったり、ブランチを特定できなかったりする場合は、不足している対象情報をユーザーに確認する。
記録の対象は選択したworktreeとし、実装の事実を書く前に関係するローカルファイルを確認する。
別ブランチの事実を、このブランチの事実として書き換えない。
会話と保存先が異なる作業を指しているようなら、記録する対象を確認する。
別worktreeであることだけを理由に別セッションへの切り替えを要求しない。
ホストが書き込みの承認を要求する場合は、通常の権限確認の仕組みを使う。

見出しと `Branch` は選択したブランチ、`Source commit` はそのHEAD、`Updated at` は現在日時（`YYYY-MM-DD HH:mm:ss`）とする。
選択したworktreeの状態を確認し、未コミットの作業はその旨を記録して、`Source commit` に含まれるかのように書かない。
保存から投稿までブランチとHEADの整合性を保つ。
途中で変わった場合は対象を再確認し、記録を更新してから進める。

### ファイル名の規約

`conversation-context-import` と同じく、ブランチ名の以下の文字をそれぞれ `-` に置換する。

```
/ \ : * ? " < > |
```

例: `dependabot/npm_and_yarn/feed-5.2.0` → `dependabot-npm_and_yarn-feed-5.2.0`

既定の保存先は `{worktree root}/.dev/contexts/{サニタイズ済みブランチ名}.md` とする。
ユーザーが別のファイル名を明示した場合はそれに従い、import時にはそのファイルの明示指定が必要なことを報告する。
異なるブランチ名がサニタイズで同じファイル名になる場合があるため、既存ファイルの更新前に見出しとブランチのメタデータが対象ブランチを指しているか確認する。
ファイル名が衝突した場合は別ブランチの記録を上書きせず、別の保存先を確定する。

### PRメタデータと取得失敗

ローカル保存だけなら、PR検出やGitHub認証を必須にしない。
対象PRが会話内ですでに確かに分かっている場合は、選択した対象のPRであることを確認して記録する。
それ以外は `PR not checked at export time` とし、PR不在と推定しない。

共有やPRメタデータの取得依頼に応じて取得が必要な場合は、`{worktree root}` から `gh` を実行する。
例えば `gh pr view --json number,url,headRefName,headRefOid,headRepository,headRepositoryOwner` でPRの識別情報とhead情報を取得できる。
投稿前に、リポジトリとheadブランチが選択したworktreeに対応し、`Source commit` がPR headまたはその祖先であることを確認する。
ローカルのcommitがPRに含まれていない場合は、ローカル保存を行って不一致を報告し、exportの一環としてpushしない。

PRフィールドでは以下を区別する。

- `#{番号}`: 対象PRを特定して確認できた。
- `PR not created at export time`: 対応するPRの不在を確認できた。
- `PR not checked at export time`: 取得する必要がなく、取得しなかった。
- `PR unverified at export time`: 取得に失敗し、PRの存在や対象が未確認である。

`gh pr view` のエラーだけでPR不在と判断しない。
明示的な該当なしの応答か、正常に完了した問い合わせで対応するPRが見つからないことを、不在の根拠とする。
接続、認証、権限、その他の取得失敗では、観測した理由を報告し、エラーだけから認証情報の無効を断定しない。
環境の制限が失敗の原因と考えられる場合は、認証情報や設定を変えず、許可された実行経路で再試行する。
それでも取得できなければ、独立して実施できるローカル保存を完了し、依頼された共有は未完了とする。
失敗の理由と共有の未完了を「残作業」に記録し、ユーザーにも報告する。
exportを可能にするためだけにPRを作成しない。

## コンテキストの保存

保存先に既存ファイルがあれば、書く前に読む。
下の既存記録の規則を適用し、テンプレートに従って書き出す。
必要なら親ディレクトリを作成する。
次の作業者に役立つ推奨スキルがあれば理由を一言添え、なければそのセクションを省略する。

コードだけでは復元できない目的、決定、却下した代替案とその理由、制約、残作業を残す。
検証した実装の挙動と、仮定や未確認の作業を区別する。
コードの一覧や作業の苦労話を繰り返さない。
ローカル保存だけの場合も、秘匿情報や個人情報を含めない。

### 既存記録の規則

- この会話内で作成した記録は、会話の全文脈と現時点の理解から再生成する。
- 別セッションの記録では、先行する発見を保持して新しい情報を追記する。
  発見の修正や削除は、検証で誤りを確認した場合に限り、推定だけでは行わない。
  誤分類された内容は、失わずにセクション間で移動してよい。
  意図、方針、範囲の変更で未確定のものだけを確認し、ユーザーが明示的に決めたことは再確認しない。
- 記録は取り消し線や逐次の変更履歴を含めず、現在の状態を表す。
  `.dev/` はコミットしないため、上書きした発見の復元をGit履歴に頼らない。

### ADRに記録された決定

既存の記録の役割分担を保つ。
決定がADR（`domain-modeling`）に属する場合は、コンテキストに一行の要約とADRへのリンクを残す。
そのアーキテクチャ判断を説明する根拠と代替案はADRに置き、それ以外の却下案はこちらに残す。
リンクにより、レビュアーは揮発する記録から設計意図を辿れる。

## PRコメントでの共有

共有が依頼または許可されており、対象PRを確認できた場合だけ、この節を実行する。
PR不在を確認できた場合は、ローカル保存を保持し、対応するPRがないため共有を完了できなかったと報告する。
PRが未確認の場合は、不在の確認と区別し、取得失敗と共有の未完了を報告する。

投稿前に保存したファイルを読み、秘匿情報や個人情報を確認する。
選択したworktreeからリポジトリと認証中のGitHubユーザーを特定し、対象PRの全ページのコメントを確認する。
本文中の部分文字列ではなく、先頭の見出し行 `# {ブランチ名} 対話コンテキスト` 全体で照合する。
ブランチ名にはサニタイズ前の名前を使う。

認証中のユーザーが書いた該当コメントのうち、最新のものを優先する。
本文を読み、ローカルファイルと同じ既存記録の規則を適用して、別セッションの発見を保持してから更新する。
追加の発見を統合する必要があればローカル記録も更新し、投稿内容と一致させる。
別ユーザーのコメントや無関係なコメントは編集しない。
自分の該当コメントがなければ、許可された共有の範囲で別コメントを作成し、同じ共有許可を取り直さない。
編集できない特定のコメントの更新を求められた場合は、黙って新規投稿に置き換えず、その制約を確認する。

シェルのエスケープ問題を避けるため、本文はファイルから渡す。

```bash
# {worktree root} から実行し、{context file} は確定したローカル保存先とする。
gh pr comment {PR番号} --repo {owner}/{repo} --body-file "{context file}"
# 対象と所有者を確認した、自分の該当コメントを更新する場合:
gh api repos/{owner}/{repo}/issues/comments/{コメントID} --method PATCH -F "body=@{context file}"
```

投稿に失敗した場合はローカル記録を保持し、失敗と共有の未完了を「残作業」に記録して、共有は未完了と報告する。
保存先pathと、共有できた場合はPRコメントのURLを報告する。
ローカル保存だけの完了、PR不在の確認、共有の失敗や未確認を区別し、成功結果なしに投稿完了と報告しない。

## 関連スキル

- **conversation-context-import**: 保存された文脈を読み込み、開発やレビューを続ける。
- **sanity-review**: 対話コンテキストとリンクされたADRから、実装意図を含めてレビューする。
- **durable-knowledge-export**: ブランチを越えて残すべきシステム自体の発見を扱う。
  振り分けはそちらの基準に従う。
- **domain-modeling**: コードとともにコミットする、このコードベースの用語集とアーキテクチャ判断を扱う。
  この揮発する記録からADRへリンクする。
