# 永続知見の書き出し

発生元ブランチを越えて将来の作業に使う知見を、事実の変化に応じて更新する話題別のページへ保存する。
この利用環境では、こうしたページを原則としてプロジェクトのリポジトリ外へ置き、ブランチの引継ぎメモやコードとともに版管理する記録と分ける。
これは保存先の方針であり、リポジトリ内の文書が長く使えないという意味ではない。
保存先が明示されていれば従い、リポジトリ内の文書なら、そのプロジェクトの文書化の手順で扱い、別の場所へ移さない。

## 依頼の範囲と許可

依頼、会話、プロジェクトの指示から、どこまでの保存が任されているかを判断する。
有用な知見を発見しただけでは、どこかへ書き込む許可にならない。
ブランチの引継ぎメモは`conversation-context-export`、このプロジェクトの合意済み用語とアーキテクチャ決定記録は`domain-modeling`が扱う。
別のSkillへ振り分けたり内容を分割したりしても、追加のファイル作成、commit、公開の許可にはならない。
これらのSkillも、すでに依頼範囲に含まれる記録についてだけ使う。

指定されたwikiの更新依頼には、下書きやローカル編集に限る指示がなければ、その更新を公開するためのcommitとpushが含まれる。
既存の許可を使い、「確認なしでpush」と言い直すことを求めない。
ローカルのknowledgeリポジトリへの保存依頼はファイル更新を許可し、そこでのcommitとpushは依頼と既存の許可に従う。
remoteが設定済みというだけではcommitもpushも許可されず、一般的な保存依頼だけでは、このSkillが選んだサービスへの公開まで許可されたことにならない。
公開やcommitの範囲が不明な場合は、ページと案内リンクの変更をレビューできる形にしてから、その操作について確認する。

## 保存先の選択

指定されたwiki、リポジトリ、すでに定まった保存先の方針に従い、選び直させない。
複数リポジトリにまたがる知見でも、wikiが指定された保存先なら置ける。
wikiが1つのリポジトリに属することは、内容の制限ではない。

保存先が指定されていない場合は、次の方針に従う。

- 現在のプロジェクトの知見は、利用可能と確認できたGitHub wikiを優先する。
  wikiがない場合は、設定済みのknowledgeリポジトリを使う。
  無効化や未初期化が確認できた場合もこれに含む。
- 複数プロジェクトにまたがる知見は、設定済みのknowledgeリポジトリを使う。
- `AGENT_KNOWLEDGE_REPO`は、記述対象の各プロジェクトの外にある、既存のローカルGitリポジトリを指す。
  渡されたパスがそのリポジトリのルートであることを、書き込み前に確認する。
  保存先を確定できなければ、利用者に下書きを提示し、不足する保存先を尋ねる。
  リポジトリの新設、wikiの有効化、認証の変更を行わず、代わりに`docs/knowledge/`を勝手に作らない。

GitHubの調査が必要な場合は、依頼とGit remoteから対象リポジトリを特定し、forkや複数remoteによる曖昧さを解消してから選ぶ。
たとえば`gh repo view "{host}/{owner}/{repo}" --json url,hasWikiEnabled`はwikiの設定を確認するもので、ページの存在やGitでの接続成功を確認するものではない。
wikiのclone URLを使い、たとえば`git ls-remote "{wikiのclone URL}"`で接続を確認する。
認証、通信、取得の失敗では利用可否は不明なままで、出力が空というだけでも原因は確定しない。
必要に応じて許可された実行方法で再試行し、解決しなければ接続を確認できないことを報告し、無断で保存先を切り替えない。
wikiが明示されている場合は、利用できなくても選択を維持し、必要な場合だけ代替先を相談する。
明示されたローカルの保存先だけで作業できる場合は、GitHubへの接続確認をしない。

## 保存先ごとの規約

**GitHub wiki**では、提供されているclone URLと利用者の既存のGit接続方法を使い、wikiのcheckoutを編集する。
GitHubの[公式手順](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages)は、GitHubで初回ページを作成してからcloneする流れを案内している。
初期化が必要だと確認できた場合はその案内に従い、cloneの失敗だけで未初期化と診断しない。
公開先は確認済みのwikiのデフォルトブランチとし、ブランチ名を固定しない。
新しいcheckoutでGit identityが未設定なら、プロジェクトで使用しているidentityを`git -c user.name=… -c user.email=… commit`でそのコマンドだけに適用し、推測で作ったりグローバル設定を変えたりしない。

**knowledgeリポジトリ**では、まず既存のページ配置と案内リンクに従う。
規約がない場合の既定配置は、リポジトリの識別情報に合わせる。

```text
{knowledge repo}/README.md
{knowledge repo}/{host}/{owner}/{repo}/README.md
{knowledge repo}/{host}/{owner}/{repo}/{Topic}.md
{knowledge repo}/_cross/README.md
{knowledge repo}/_cross/{Topic}.md
```

記述対象リポジトリの識別情報は、意図したremoteから求め、checkoutのディレクトリ名から推測しない。
使えるremoteの識別情報がないプロジェクトでは、ownerやhostを勝手に作らず、利用者と配置を決める。
複数プロジェクトにまたがる知見には`_cross/`を使う。
この既定配置では、新規ページを同じ範囲の`README.md`からリンクし、新しい範囲を追加した場合だけ最上位の索引にも追加する。
既存のwikiやknowledgeリポジトリでは、新規ページや改名したページへのリンクが必要な場合に案内を更新し、`Home.md`へページ一覧を強制したり、本文だけの更新で索引を書き換えたりしない。

## 更新と保存

既存の話題のページは編集前に読み、確認した根拠に基づいて追記や訂正を行い、無関係な寄稿を保つ。
固定テンプレートや分類を要求せず、保存先の様式に従う。
単独で読めるだけの文脈を含め、測定や評価では、陳腐化を判断するために必要な日付、条件、出典、限界を書く。
秘密値や、その保存先への掲載を意図していない会話やローカル履歴を、ページにも索引にも転載しない。
必要な根拠を要約し、非公開の識別情報を出さない。

編集前に、保存先checkoutの作業ツリーとstage済みの変更を確認し、既存の作業と今回の書き出しを区別できるようにする。
対象のファイルやhunkだけをstageして差分を確認し、commitには、stage済みを含め既存の無関係な変更を入れない。
既存の作業を変更せずに分離できなければ、下書きの変更を残して利用者と調整する。
許可されたpushの前に、push URL、宛先ブランチ、送信されるcommitを確認し、無関係な未送信commitを含めない。
remoteの存在はupstreamの設定ではなく、upstreamがあってもGitのpush先設定と異なる場合がある([git-push](https://git-scm.com/docs/git-push)参照)。
宛先が曖昧なら、remoteを推測したり追跡設定を変えたりせず確認する。
保存したパスまたは公開を確認できたURLを報告し、ローカル編集、commit、公開成功と、未実施や失敗した操作を区別する。
