# ドメインモデリング手順書

プロジェクトの概念を明確にし、依頼された範囲で合意した用語と決定を記録する。
`CONTEXT.md`を読んで既存の語彙を使うだけなら、このSkillは必要ない。

## 依頼の範囲

他のSkillから呼ばれる場合も、依頼、会話、プロジェクトの指示から、ファイルへの記録まで任されているかを判断する。
用語の相談だけなら、ファイル編集も記録の許可を毎回尋ねることも必須ではなく、依頼された作業に必要な情報が欠ける場合だけ確認する。
ファイルを変更しない指示に従う。

記録を任されている場合は、合意した項目を固まった端から保存し、項目ごとに同じ許可を取り直したり計画全体の合意を待ったりしない。
確定した決定を記録する直接の依頼に、grillingのインタビューや計画全体の確認を前提として加えない。
仮の呼び名や未決定・撤回済みの選択肢を、正典の用語や採用済みの決定として記録しない。
記録の許可を実装、commit、push、外部投稿の許可へ広げず、それぞれについてすでに定まった範囲に従う。

## どの層か

これは**記録層**であり、記述対象のコードと同じ履歴に属し、追記とsupersedeで保全する成果物を扱う。
対になる2つの層との区別は、置き場所ではなく**更新モデル**である。

| 層 | sink | 更新モデル |
| --- | --- | --- |
| 揮発層(`conversation-context-export`) | `.dev/contexts/`、共有が依頼または許可された場合はPRコメント | ブランチごとに再生成。commit しない |
| **記録層(この skill)** | `CONTEXT.md`、ADR ディレクトリ | **追記と supersede。書き換えない** |
| 永続層(`durable-knowledge-export`) | GitHub wiki または knowledge リポジトリ | living page。常に現在状態 |

この層は、**このコードベースの語彙**と、**覆したことを記録として残したい決定**を扱う。
living pageに置いた決定は「かつて別の決定だった」という事実を失う。

抱え込まず振り分けるもの:

- *この*変更の根拠、残作業、一度きりのデバッグ → 揮発層。
- 実測値、ツール評価、システム横断の落とし穴 → 永続層。

## セッション中に行うこと

既存の用語集の定義との衝突を表に出し、曖昧・多義な語を明確にする。
確立した術語を使い、分野が等しく開いたままにしている候補の間でだけ、プロジェクトの各概念の正典となる語を選ぶ。
具体的な場面でドメインの境界を検証し、現在の動作についての言明をコードと突き合わせ、矛盾を表に出す。

記録が依頼範囲に含まれる場合は、確定した用語と条件を満たす決定をその場で書く。
長い議論で内容を失わないよう、最後にまとめて書くことを避ける。

## 用語集

`CONTEXT.md`は用語集であり、実装の詳細、仕様、走り書きを入れない。
書式、レイアウト、既存の定義の保護は [CONTEXT-FORMAT.md](CONTEXT-FORMAT.md) を読む。

記録が依頼範囲に含まれ、最初の合意した用語を保存する必要があるときだけ作る。

## ADR

**3条件すべて**を満たすときだけADRを提案する。

1. **覆しにくい** — 後から考えを変える費用が無視できない。
2. **文脈なしでは意外** — 将来の読み手が「なぜこうしたのか」と思う。
3. **本物のトレードオフの結果** — 実在する代替案があり、特定の理由でこれを選んだ。

1つでも欠けたら、自分からADRを提案しない。
明示的なADR記録の依頼が条件を満たさないように見える場合は、不足する条件を伝え、必要な場合だけ記録の意図を確認する。
依頼を無言で取り落としたり、事情を理解したうえでの選択を再確認したりしない。
多くのセッションでは、ADRは不要か少数で済む。

採番、supersede、テンプレートは [ADR-FORMAT.md](ADR-FORMAT.md) を読む。

### ADR ディレクトリを解決する

**`docs/adr/` を決め打ちしない。**
違う場所に書くと記録が二分される。
ADRの記録が依頼範囲に含まれる場合は、以下の順で解決する。

1. **既存のADRディレクトリ。**
   `docs/adr/`、`doc/adr/`、`docs/decisions/`、`docs/architecture/decisions/`、`adr/`を探す。
   ADRが入っているものがあればそれを使い、既存ファイルを何本か読んで採番・front matter・見出しの様式に合わせ、テンプレートを押し付けない。
2. **ツールの設定。**
   `.adr-dir`(adr-tools)がディレクトリパスを持ち、`.log4brains.yml`(Log4brains)はプロジェクト設定の中で指定する。
3. **どちらも無い** → `docs/adr/` を既定として作成し、そうしたこととその理由をユーザーに伝える。

最初の ADR を書く前に、解決したディレクトリを述べる。

## 関連スキル

- **grilling**: 依頼範囲に応じて、合意した項目の記録をこのSkillに任せるインタビュー。
- **conversation-context-export**: 依頼に応じて揮発する文脈を保存し、記録済みADRの論拠を複製せず、要約とリンクを残す。
- **durable-knowledge-export**: リポジトリ外のシステム横断の知識を担当する。
