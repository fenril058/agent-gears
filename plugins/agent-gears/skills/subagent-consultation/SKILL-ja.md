# subagent 相談

相談内容、相談先の選定、追加相談の判断、回答の統合を担当する。
実行にはhostで利用できるAgentツールか実行adapterを使う。

## 目的と範囲

ユーザーの質問と既に定まった作業文脈から、対象と必要な判断を決める。
これらが明らかなら、相談の深さを選ぶ質問を挟まず進める。
相談を左右する情報が欠けており、文脈からも補えない場合だけ確認する。
対象、モデル、実行手段、禁止操作の明示的な指定を守る。
モデルと実行手段の指定は相談先の起動時に適用し、対象と該当する操作制約を相談先への指示に含める。

探索は依頼された範囲と、その判断に必要な関連コードや出典に限る。
関数1つについての依頼は、リポジトリ全体の監査を許可しない。
相談やレビューの依頼だけでは、修正の実装、commit、push、外部投稿は許可されない。
作業で既に任されている調査や操作は、再度許可を求めず進める。

## 相談先に渡す情報

質問、対象資料または正確なrevision、評価基準、関連する制約、許可された操作を渡す。
この会話を知らない相談先でも理解できるプロンプトにする。
結論を証拠と結び付け、結論に影響する情報不足や検証失敗も報告するよう求める。

目的に応じて依頼の形を選ぶ。

- **独立レビュー**：対象の生の資料と評価基準を渡し、主担当の指摘、疑っている箇所、期待する答え、結論は渡さない。
  自動的な会話履歴の継承も含め、起動手段が実際に渡す会話や背景情報を確認する。
  プロンプトから仮説を省くだけでは、継承された文脈から仮説を除けない。
  利用できる場合は、その履歴を引き継がない新しい文脈を使う。
- **設計相談や案への批評**：反論や代替案を検討できるよう、評価する案、その理由、制約を渡す。
  主担当の仮説と確認済みの事実を分ける。

すべての相談に同じ形を強制しない。
例えば「この差分を一度レビューして」では独立した読解を求め、「この設計を評価して」では設計を渡す。
利用できる手段で指定された独立性を満たせなければ、結果を独立したものと呼ばず、その制限を報告する。

## 相談先と実行手段

起動、続行、回答取得の方法を選ぶ前に、現在のhostのツール定義と利用できる機能を確認する。
`Agent` という名前のツール、特定のschema、固定のモデル名の存在を前提にしない。
必要な判断に適した相談先を使い、ユーザーや呼び出し元の指定に従う。
次の機能は別々に扱う。

- **モデルの選択**：hostがモデルの指定を許していても、それだけでは履歴の継承やモデル系列は分からない。
- **新しい文脈**：主担当の会話を引き継がない相談先は、主担当の結論を見ずに資料を読み直せる。
- **別のモデル系列**：利用でき、目的にも合う場合は異なる盲点を見つける助けになり得るが、推論や誤りの独立性を保証しない。

指定されたモデル、系列、文脈の条件を、黙って弱い条件に置き換えない。
要件を満たす相談先がなければ、何を満たせないかを示し、主担当の分析と未実施の相談を区別する。

### hostごとの実行

Claude Codeでは、現在の `Agent` ツールが利用でき、目的に合う場合に使う。
モデル指定や続行の方法はここで固定せず、ツールの定義を確認する。
Claude CodeからCodex CLIを選ぶ場合は、[codex-consultation](../codex-consultation/SKILL.md) を使う。
完全なプロンプト、対象worktreeの絶対path、test/build/diagnosticが必要になり得るか、remote情報が必要かを渡す。
adapterは実行能力、1回の実行の制限時間、後片付け、実行事実の返却を担当する。
各呼び出しはforegroundで同期的に回答か明示的な失敗まで完了し、永続threadを保持せず、後で回収するbackground jobを返さない。

Codexでは、公開されているsubagent操作を、会話履歴の継承に関する指定も含めてツール定義に従って使う。
追加相談では実際に作業を開始または再開する操作を選ぶ。
メッセージの配送だけでは待機中のAgentが動き出さない場合がある。
threadが別であるだけでは、新しい文脈や別のモデル系列を使ったことにはならない。

## 検証と追加相談、停止条件

回答の主張を採用する前に、一次資料と照合する。
裏付けのある指摘、未解決の仮説、取得できなかった証拠を分ける。
相談先の同意だけでは検証にならず、意見が異なる場合は理由と証拠を比較する。

次の結果を区別する。

- **使える回答がない場合**：実行失敗を報告する。
  未試行の適切な相談先が、依頼の制限内で要件を満たせるなら使う。
  代替の選定はこのSkillが担当し、実行adapterには持たせない。
  試し終えた手段を繰り返したり、黙って要件を緩めたりしない。
  適切な選択肢が残っていなければ、相談が未実施であることを報告し、主担当が行えた分析だけを示す。
- **一部の実行に失敗しても使える回答がある場合**：使える部分を残し、どの結論が不足情報に依存するかを特定する。
  可能なら既存の権限内で情報を取得し、影響する結論を修正した上で、未確認の部分を報告する。
  fetch、test、diagnosticの1つが失敗しただけで、回答全体を捨てたり相談先を切り替えたりしない。

依頼が許す場合は、重要な反論、証拠不足、未回答の問いを解くために追加相談する。
一度のレビューで十分な回答が得られたなら、追加相談は不要である。
深い相談では重要な未解決点を追い、既定の往復回数を満たすことを目的にしない。

既存の文脈が論点の解決に役立ち、実行手段が続行を支える場合は、同じ相談先を続行する。
独立した判断が必要なら、新たに読む相手を使う。
主担当の仮説を既に見た相談先を、その仮説を知らずに読む相手としては扱えない。
続行時は、絞った質問と新しい証拠を渡す。
新規実行では必要な背景、質問、制約、証拠を再掲し、前の回答は目的が許す場合だけ含める。
Codex adapterは、同じ論点の追加相談でも毎回新規実行になる。

明示された回数の指示を守り、その上限で止め、残る論点を報告する。
それ以上の相談回数が要求されていなければ、問いに十分答えられた時点、相談を続けても進展しなくなった時点、残る不足を利用できる許可済みの手段で解決できなくなった時点で止める。
網羅性を求めて質問や相談先を増やし続けない。
際限なく再試行したり、権限変更やhost設定変更による回避策を作ったりせず、残る不確実性を報告する。

## 報告

相談に応じて報告量を決め、短いレビューなら1段落や数項目で伝える。
相談内容と実際に回答した相手、主要な意見、重要な意見の相違も含む主担当の根拠に基づく判断、結果に影響する制限を示す。
追加相談の結果や失敗した試行は、その判断に関係する場合に含める。
見出しは役立つ場合だけ使い、固定の報告書や主担当の名前を含む見出しは必須にしない。
