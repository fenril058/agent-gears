# Empirical Prompt Tuning

プロンプトの品質は書いた本人には分からない。
書き手が「明瞭だ」と思うものほど、別のエージェントが読むと詰まる。

しかし、疑わしいものすべてを測る価値があるわけではない。
「指示あり」と「指示なし」の比較が証拠になるのは、指示なしの arm が実際にその指示へ到達できないときだけであり、それを成立させるのは指示を書くことより難しい。

だから順序を守る。
静的に監査し、host が既に提供しているものを使い、その両方を通過してなお具体的な未解決点が残るときにだけ測定を組む。

## いつ使うか

- skill / slash command / タスクプロンプトを新規作成・大幅改訂した直後
- エージェントが期待通り動かず、原因を指示側の曖昧さに求めたいとき
- 重要度の高い指示(頻繁に使う skill、自動化の中核プロンプト)を堅牢化したいとき

一回限りの使い捨てプロンプトには使わない。
書き手の主観的な好みを反映させるためにも使わない。

## 1. 静的な整合確認

必ず最初に行う。多くの場合これだけで足りる。
サブエージェントの起動も実行も要らない。

- frontmatter の `description` が主張するトリガーと用途を読む。
- 本文が実際に覆っている範囲を読む。
- 食い違いがあれば、他の何よりも先に解消する。

ここに隙間があると、以降がすべて汚染される。
実行者は description に合わせて本文を読み替えてしまい、指示は要件を満たさないまま高い点を取る。

host が自ら注入するもの —— system instruction、tool description、隣接する常時ルール —— と突き合わせても読む。
それらと重複または矛盾する指示は、何も実行せずに見える欠陥である。

## 2. first-party tooling

何かを作る前に、host が自分の指示を実行・追跡・評価するために提供している機能を使う。
runtime を変更する当事者が保守しており、必要な trace を出すことが多く、動き続けさせる費用がかからない。

## 3. custom measurement

手順1と2を通過してなお具体的な未解決点が残るときだけ、ここに来る。
以下をすべて、実行する**前**に確定する。
ひとつでも確定できないなら、実行しない。

### 結果が変更する判断を明示する

どの結果が出たら配置判断のどれが動くのかを書き出す —— 維持、範囲を狭める、明示起動のみにする、特定 host に限定する、削除。
どちらに転んでも判断が変わらない測定は、費用に見合わない。

### 要件を事前に固定し、実行者には見せない

成果物が満たすべき項目を実行前に列挙し、あとから動かさない。
要件を実行プロンプトに入れてはならない。
checklist を渡された arm はそれをそのまま実装できてしまい、比較が検出しようとしていた差が潰れる。
採点は実行後に、成果物を見て行う。

### 観測可能な証拠で採点する

出力中の「リポジトリを確認した」という主張は、確認した証拠ではない。
実行者自身の申告より、tool call、ファイルの状態、trace を優先する。
要件ごとに何を証拠とみなすかを事前に決め、その証拠が取れなかった要件は未評価とする。
未評価は失敗ではなく、合格でもない。

### 比較に必要な隔離を成立させる

最も多く仮定され、最も多く未達になる条件である。
次の4つすべてが必要になる。

- **候補なし arm から、候補が到達不能であること。** 未ロードではなく到達不能。host のカスタマイズ無効化が止めるのはロードだけで、探しに行く実行者は見つけてしまう。経路をすべて塞ぐ —— host の設定下にインストールされた複製、他の arm が使用中または残した複製、シナリオが実行者を置く checkout 内の複製、tip から消えても Git の履歴・refs・remote から到達できる複製。
- **評価条件を全 arm から秘匿すること。**
- **対象名が、候補自体を除くどこからも漏れないこと。** 候補を渡された arm がその front matter から名前を読むのは treatment であって違反ではない。あってはならないのは、別経路から名前が届くことである —— 作業ディレクトリと兄弟の名前、プロセス引数、継承した環境変数、Git metadata、隣にインストールされた無関係な指示の description、シナリオが実行者に読ませる world 内のドキュメント。
- **それ以外に実行者が観測できるものが、arm 間で等価であること。** 候補が委譲する先も含む。候補が呼び出す依存は環境の性質であり、全 arm へ等しく与える。

### 時間箱と停止条件を先に決める

どちらも初回実行の前に決める。
「数字が良くなるまで」は停止条件ではない。

### 隔離を成立させられないなら、そう報告する

隔離できない比較を実行し、注釈付きで数字を出すことはしない。
不成立を結果として報告する —— 問い、塞げなかった経路、答えるには何が変わる必要があるか。
壊れた baseline の上で出た数字は、数字が無いことより悪い。
あとから注釈抜きで引用されるからである。

## 結果の読み方

- 総合スコアではなく要件ごとに比較する。総合スコアはどの要件が動いたかを隠し、非 critical な1件の変化が全体の勝ちに見える。
- host や model をまたいで平均しない。同じ修正が或る model では改善し、別の model では悪化しうる。平均するとその悪化が消える。比較の単位は、ひとつの host のひとつの model 上のひとつの case である。
- 結果には必ず host と model を記録する。model を特定できないなら、そう明記し、その結果を比較に使わない。
